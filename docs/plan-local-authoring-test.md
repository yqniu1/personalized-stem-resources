# Local prompt-to-lesson test

Date: 2026-10-20

Peter asked to keep building autonomously until he can enter a prompt, use local tools, and generate a lesson on the canvas. This advances the earlier design into a local operator test, before a teacher trial.

## Implementation boundary

Use the existing niu-prototyper canvas and its Codex terminal. Codex's installed WSL CLI reports it is signed in; model execution is still to be tested. Do not add a model proxy or change the shared terminal engine. The prompt surface is the native terminal drawer, not a new chat form.

Add a standard-library Python workspace helper in this repository. It initializes an external local workspace with source, materials, requests, revisions, exports, agent instructions, and a starter preview. A PowerShell launcher initializes it, registers a distinct prototyper project, and opens the canvas. The default workspace lives in local app-data; original Lily files and the private Lily registry entry remain separate.

The first supported deliverable is one self-contained HTML lesson. The agent may read supplied local materials, write HTML/CSS/JavaScript, run checks, and publish through the helper. A lesson can be new or based on the bundled Lily reference. Other native agents may follow the file contract later; only the tested provider will be advertised.

Publication records the prompt, base preview hash, generated bytes, summary, and revision. Failed validation or a changed base preview must leave the existing preview intact. Repeating publication of a completed task must not create a second revision. Basic structural checks do not establish accessibility, scientific accuracy, or a fully offline artifact; those require separate checks.

One active editing agent owns the runtime workspace. Helper operations use a local lock; this is not a sandbox or a defense against agents bypassing the helper. Closing the drawer or server does not cancel an agent. The native agent's interrupt/exit controls remain authoritative.

## Tests defined before implementation

1. Initialize and reopen without overwriting existing user work.
2. Begin a task, write a lesson, publish, and prove preview/export/snapshot byte identity.
3. Reject malformed or missing lesson output and preserve the previous preview.
4. Reject stale preview publication and preserve an external edit.
5. Repeat a completed publication without another revision; reject a second active request.
6. Verify local lock exclusion and interrupted-task recovery without deleting draft work.
7. Run a real Codex prompt from the canvas terminal: read a local material, write an interactive lesson, invoke the helper, and reload the canvas.
8. Exercise the generated interaction, issue a revision prompt, and inspect the updated lesson and retained earlier version.
9. Open the export separately with network disabled; check the selected interaction and reset.
10. Leave the canvas and one idle agent ready for Peter to type his own prompt; provide a reusable launch command.

## Risks and review limits

- WSL CLI authentication may exist while model execution fails. Test it before reporting readiness.
- A terminal can satisfy Peter's operator test while still being unsuitable for independent teachers. This remains an assisted prototype.
- Agent-written HTML can run arbitrary JavaScript. Keep it on the existing separate target origin, serve only preview files, and do not put credentials in that directory.
- A process interruption between preview and state writes can leave an inconsistent publication. Preserve snapshots and fail loudly on mismatched hashes; do not claim database transactions.
- An agent may ignore instructions. Verify real output and keep original sources outside its normal working directory. Instructions are not access controls.
- New-lesson generation is not evidence of instructional quality. No teacher acceptance or learning claim follows from this test.

**Insight:** reuse the native agent as the tool runner and keep lesson state in ordinary files. A new chat service would add authentication and process-management work without helping this first local test.

BrowserOS's synthesized typing initially doubled letters in xterm. The malformed
draft was cleared before execution. Single input events plus native Enter key events
submitted the actual test prompts. This is a known automation limitation, not a
verified defect in human typing. Screenshot capture did not yield an inspectable image;
the checks above used rendered accessibility/DOM state and actual interactions.

The first lesson's initial refresh failed and required a connection repair. The later
revision completed publication and automatic refresh without that intervention.
These are operator tests, not measured teacher task times or learning evidence.
Cross-provider operation, new-resource quality across subjects, all-device accessibility,
and human instructional review remain open. The original Lily module's keyboard gap
is separate from the new generated lesson's tested controls.

**Insight — contract boundary:** process visibility inside a sandbox is not the same
as service availability. An authenticated health/API request checks the boundary this
workflow actually needs, without granting the agent broader process access.

## Knowledge and skills audit after Peter's teacher questions

The current prompt-to-lesson test did **not** exercise personal knowledge retrieval.
Inspection of the actual native Codex run showed reads of the workspace instructions,
synthetic classroom brief, and copied Lily HTML, followed by generation/publication.
No Learnability Patterns file reads or niu-library calls appeared.

The canvas agent runs under WSL's Codex configuration. `codex mcp list` reported no
configured MCP servers. Its advertised skills were built-in/plugin skills; Peter's
personal Windows skill collection was not in that catalog. This parent development
conversation used personal workflow, canvas and review skills, but those tools and
instructions are not automatically inherited by the separate native agent.

The knowledge exists: 22 pattern Markdown files are under
`C:/Users/pniu/Projects/website/personal/src/content/patterns/`. Lily's preserved July
14 design explicitly grounded its decisions in those files and niu-library's de Jong
chapter on simulation-based learning. It mapped Coherence, Pretraining, Transfer,
Generative, and Practice & Feedback to specific changes, and cautioned that its
research argument relied on one retrieved passage. The current public Lily alignment
summary is less detailed than that preserved design.

Thus the workbench is operational for local generation, but its intended personal
knowledge/skills integration remains missing. The parent conversation verified
niu-library retrieval during this audit; that is not evidence of retrieval during
lesson generation. No connector or skill configuration was changed by this audit.
